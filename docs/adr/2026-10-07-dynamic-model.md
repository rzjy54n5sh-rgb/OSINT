## 1. Context and binding rulings (2026-10-06)

- **R1 — "dont accept any invented claim".** Every probability or claim stores its inputs and sources. The database rejects rows without them wherever a CHECK constraint or trigger can express the rule. This follows the `nai_scores_v2` precedent.
- **R2 — Scenarios are dynamic.**
  - Birth: a `detected_scenarios` candidate, backed by at least two independent non-party sources plus a new actor or instrument, which the operator approves. A new prediction market on a new question can also propose a candidate.
  - Retirement: below 10% for 14 consecutive days makes a scenario fading. A fading scenario is retired only when the operator confirms. If its defining market or condition resolves, it becomes fading immediately.
  - Retired scenarios stay visible.
  - Note: the plan document still says 2%. The ruling (10%) supersedes it and is the value encoded here.
- **R3 — Probabilities come from the market-anchored method only.** The operator can override at two levels:
  - input level: reclassify or exclude a market;
  - output level: supply the numbers plus a reason.
  - J1 is ratified: a ceasefire-breaking US or Israeli strike counts toward D.
- **R4 — A–D are mutually exclusive and sum to 100.** E is independent and overlaps them.
- **R5 — History is migrated unchanged.** Days 1–35 and 221 keep their values, and every current reader keeps working through the transition.
- **Reports.**
  - Report types are dynamic.
  - Backfill depth: a daily General brief, plus weekly country, eschatology and business briefs.
  - Every report is labelled contemporaneous or reconstructed.
  - EN and AR documents are stored in Supabase Storage (free tier, 1 GB).
- **Live intelligence.**
  - Articles are grouped into stories.
  - Each story tracks first seen, outlets, the party versus independent mix and the language mix.
  - Geolocation is recorded only when an article states it.
  - Topics emerge and fade.
  - Threshold events raise alerts or candidate scenarios.
- **Constraints.** Free tiers only. No metered AI API in automation. The database cap is 500 MB; production was 38.75 MB on 2026-10-06.

## 2. Decisions (summary)

1. **Registry plus a daily fact table instead of fixed columns.**
   - `scenarios` holds identity and lifecycle. Each scenario belongs to a `scenario_groups` row: `core` is exclusive with a sum target of 100; `independent` has no sum.
   - `scenario_daily` holds one row per scenario per day per method, run and override. At most one row per scenario per day is published.
   - **The sum rule is enforced at COMMIT by a deferred constraint trigger.** For an exclusive group on a published day:
     - every live member must have a published row;
     - none of them can be NULL;
     - they must sum to exactly 100.
   - No row can be published outside a scenario's life (from `born_day` to `retired_day − 1`).
2. **The R1 rules are enforced in the database, not by convention:**
   - **Market-anchored rows** need a run, a horizon, and an input list that passes `scenario_inputs_valid()`, which uses the `scenario_d221.json` element shape. A number must have a basis: at least one used market reading or a derived step.
   - **Operator-override rows** need a `scenario_overrides` record with a reason of at least 10 characters and an `admin_users` id.
   - **The `legacy-desk-v0` method** is accepted only for Days 1–35, only with `legacy_row_id` set, and only inside the import transaction.
   - Any future method family must carry inputs unless it is explicitly exempted.
   - All multi-branch CHECKs are wrapped in `coalesce(…, false)`. A CHECK that evaluates to NULL passes, and testing found four such leaks, now fixed (tests S34–S36, R09b, R13b, T06b).
3. **Each run stores the full input table** in `scenario_runs.inputs`: used, excluded and context markets alike. This lets a verifier recompute the published numbers. Runs and rows are immutable; the only change allowed is flipping `is_published`.
4. **Provenance cannot be backdated.**
   - `recorded_at` is forced to `now()` except inside an explicit import.
   - `provenance = provenance_for(conflict_day, recorded_at)` is a CHECK.
   - The cut-off is 06:00 UTC on the calendar day after the conflict day. It is expressed in UTC explicitly, so it never depends on the session timezone.
   - The same rule fills `daily_briefings.provenance`.
   - A reading for a future day is rejected.
5. **Status changes only go through functions.**
   - The functions are `scenario_transition()`, `scenario_promote_candidate()`, `scenario_lifecycle_tick()` and `report_type_transition()`. Guard triggers reject direct UPDATEs.
   - Every change writes an append-only event that records the actor, the reason, the evidence and the rule snapshot.
   - Retirement and birth require an operator.
6. **Compatibility.**
   - `v_scenario_probabilities_compat` reproduces `scenario_probabilities` exactly: same columns, same order, same types, same ids and same `updated_at`.
   - During the transition, a deferred sync trigger keeps the physical table up to date from the published A–E rows. Existing readers (the site, Edge Functions, KV warmer, digest) are untouched.
   - Only legacy or contemporaneous rows reach the legacy shape, because that shape cannot carry a "reconstructed" label.
7. **Reports.**
   - The `report_types` registry is seeded with the 5 existing types.
   - `daily_briefings` gains columns only: `provenance`, `period_start_day`, `period_end_day`, `title_ar`, `lead_ar` and `sections_ar`. It also gains CHECKs, a foreign key to `report_types`, and a unique index on `(conflict_day, report_type)`. Production has 0 violations of any of these.
   - Documents are rows in `report_documents` with a deterministic path, a sha256, bytes, the generator, and the validation result. Arabic documents require an RTL pass. Rows are versioned and superseded, never deleted.
   - The bucket `reports` is private. Files are served through signed URLs.
8. **Stories.**
   - Counts and the language mix are derived by a statement-level trigger from `story_articles`; they are never hand-written.
   - A story's title is forced to the verbatim headline of a member article.
   - Geolocation requires a `geo_quote` that actually appears in the stating article's title or summary.
   - `articles.lat` and `articles.lng` are outlet headquarters constants (DB audit #13) and are never used for story geolocation.
   - Outlet classification lives in `outlets` and `outlet_aliases`. Only 102 of 584 articles match `article_sources`. The default classification is `unknown`, never a guess, and each classification must cite its basis.
9. **Retention.**
   - None of the new tables can be deleted from: triggers block it, and DELETE and TRUNCATE are revoked even from `service_role`.
   - A clustered article cannot be deleted, because the foreign key uses `ON DELETE RESTRICT`. If the old cleanup cron were ever recreated, it would fail loudly.
10. **RLS.**
    - Public read where appropriate.
    - Writes are allowed only through policies that name `service_role` explicitly.
    - Table privileges are revoked from `anon` and `authenticated` on every new table and on `scenario_probabilities`, `detected_scenarios`, `daily_briefings` and `articles`. The lesson applied: policy names prove nothing.
    - Mutating functions can be executed only by `service_role`.
    - Not public: the alert review queue, report-type events, proposed market links and candidate report types.

## 4. State machines

**Scenario** (`scenarios.status`; every arrow writes a `scenario_lifecycle_events` row):

```
detected_scenarios: candidate --(operator: scenario_promote_candidate; evidence rule)--> approved
                                                     |
                                                     v
                 +---------------------------- ACTIVE <-------------------------------+
                 | job: streak >= 14 days < 10%    |  job: defining market resolved     | job: latest >= 10% and
                 | (threshold_streak)              |  with fade_on_outcome              | no resolved condition
                 v                                 v  (condition_resolved)              | (recovered) / operator
               FADING <-------------------------------------------------------------- +
                 | operator only (admin id): fading -> retired     (active -> retired is refused)
                 v
              RETIRED (terminal; retired_day = first day with no reading; history kept;
                       re-birth = new scenario with supersedes_scenario_id)
```

- **Streak rule** (`scenario_days_below_threshold`): the number of consecutive conflict days, ending at the as-of day, that have a published reading strictly below the group threshold (10). A missing day or a NULL reading breaks the streak.
- **Birth evidence rule** (`scenario_birth_evidence_valid`):
  - `detected` origin: at least 2 independent (`party_source:false`) sources on at least 2 distinct hosts, plus a non-empty `new_actor` or `new_instrument`.
  - `market` origin: at least 1 market with venue, question, URL and `read_at`. Market candidates also go through `detected_scenarios`, with `detected_by='market_watch'`.

**Report type:**

```
candidate --operator--> active <--job/operator--> paused
active | paused --operator--> retired
candidate --operator--> rejected
```

Candidates are created by `report_type_propose()` with threshold evidence. The job can never activate a candidate or retire a type.

**Market link:** `proposed → approved → ended` (closed with `valid_to_day`), or `proposed → rejected`. Only approved links are used. A reclassification creates a new row; old rows are never rewritten.

**Topic** (per day in `topic_daily.status`, with the current value in `topics.status`): `emerging → active → fading → dormant → (emerging again)`. This is computed by the deterministic job under a stored `rule_version`.

**Story:** `developing → active → cooling → closed`, or `→ merged` via `story_merge()`, which reassigns members and records `reassigned_from_story_id`. Nothing is deleted.

**Alert:** `open → acknowledged | dismissed | promoted`. Every state other than `open` requires a reviewer. `promoted` additionally requires a `detected_scenario_id` or a `platform_alert_key`. A `scenario_candidate` alert must already meet the two-independent-hosts bar.

## 5. Contracts builders implement against

- **Input element (scenario inputs)** — the shape of `/tmp/claude-0/scenario_d221.json`:
  - Market reading: `{venue, question, url (http/s), read_at, probability (0..1), used (bool), yes_bid, yes_ask (numbers, when used), excluded_reason (text, when not used), scenario_class, transform, api_url, liquidity, resolution_date}`.
  - Derived step: `{"kind":"derived","rule":"…","from":[…]}`.
  - Example: B is the residual, so its row carries a derived element. C carries the Bab el-Mandeb input, the two Hormuz gate inputs (`role:"gate"`), a gate step and a rounding step.
- **Rounding:** published values are integers produced by Hamilton rounding; `probability_raw` holds the unrounded value. `method_label` is generated, for example `market-anchored-v1+override:<id8>`.
- **Output override:** call `scenario_apply_output_override(day, 'core', '{"A":n,"B":n,"C":n,"D":n}', reason, admin_id)`. It unpublishes the computed rows (they are kept) and publishes the override. The group sum is checked at commit.
- **Report rule JSON:**
  - `{"metric":"always"}`, or
  - `{"metric":"stories|articles|independent_outlets","scope":{"topic_slugs":[…]} or {"country_codes":[…]},"window_days":1..60,"consecutive_windows":>=1,"min_value":>0}` for activation, with `max_value` instead of `min_value` for pause rules.
- **Document path:** `briefings/d{day:03d}/{report_type}/{briefing_id}/{en|ar}/v{n}.{docx|pdf}`.
  - The guard checks the brief's day and type.
  - An Arabic document needs `daily_briefings.sections_ar`. The Arabic text is written by the Claude scheduled task, never machine-translated at render time.
  - `validation` must contain `ok:true` and a `validator`; Arabic also needs `rtl:true`.
- **Story snapshot:** `story_articles.outlet_name` and `published_at` must equal the article row. `party_status` other than `unknown` needs a registered outlet. `lang_basis` is one of `script_detect`, `outlet_registry`, `article_sources` or `unknown`.
- **Alert evidence:** `[{url, outlet, published_at, party_status}]`. Each alert also stores `rule_code`, `rule_version`, `rule_snapshot` (the thresholds) and `metrics` (the observed values).

"Probabilities by Claude only via the market-anchored method" is satisfied because the method is deterministic code. Claude may run it in a session, as it did for Day 221, but the result can only enter the database as a run with inputs.

**Proposed rule defaults** (to be confirmed or calibrated on real data; each is stored with a version):
- **`topic-v1`:**
  - emerging: at least 3 stories in 3 days, with fewer than 1 story a day on average over the prior 14 days.
  - active: at least 7 stories in 7 days.
  - fading: the 7-day story count is below 25% of the 28-day peak.
  - dormant: 0 stories in 14 days.
- **`alerts-v1`:**
  - `story_spike`: at least 5 outlets within 6 hours.
  - `chokepoint_change`: a chokepoint-topic story with at least 2 outlets, at least 1 of them independent.
  - `scenario_candidate`: at least 2 independent hosts plus an actor or instrument term that is not in the known list.
  - `market_move`: the mid moves at least 10 points within 24 hours.
- **Report activation:** at least 10 stories in 7 days, for 2 consecutive windows.
- **Report pause:** at most 2 stories in 14 days.

## 7. Migration and compatibility plan

1. **Phase 0 (now).** Nothing changes.
2. **Phase 1: apply 100000 and 100100 together.**
   - This creates the registry, imports Days 1–35 (126 rows: 31 days × A–D, plus E on Days 15 and 21) and imports Day 221 (5 rows and 1 run).
   - **The 100100 migration aborts unless the compatibility view equals `scenario_probabilities` in both directions of `EXCEPT`.** It also aborts if the Day 221 row is not 23/44/5/28/NULL, and the import aborts if any legacy value would change in `numeric(6,3)`.
   - The physical table remains the read source. The deferred sync updates it from published A–E rows, but only contemporaneous ones.
3. **Phase 1b: apply 100200** in the same release in which the W2 builder switches the daily writer to `scenario_runs`/`scenario_daily`.
   - After this, any direct write to `scenario_probabilities` raises an error. It would have carried no inputs.
   - Rollback: `DROP TRIGGER scenario_probabilities_derived_only ON public.scenario_probabilities;`
4. **Phase 2 (optional, once readers move to the registry API).** Swap the view in under the old name:

   ```sql
   BEGIN;
   ALTER TABLE public.scenario_probabilities RENAME TO scenario_probabilities_legacy;   -- frozen; view keeps its OID for ids
   DROP TRIGGER scenario_daily_b_sync_legacy ON public.scenario_daily;
   CREATE VIEW public.scenario_probabilities WITH (security_invoker = true) AS SELECT * FROM public.v_scenario_probabilities_compat;
   GRANT SELECT ON public.scenario_probabilities TO anon, authenticated, service_role;
   COMMIT; NOTIFY pgrst, 'reload schema';
   ```

5. **Reports and stories.** These migrations are additive, so they can be applied independently after 100000. Stories depends on 100300 (the `report_types` foreign key).
   - Existing `daily_briefings` writers keep working, because provenance is filled by a trigger.
   - What now fails loudly: an unregistered `report_type`, a second issue of the same type on the same day, and a past-day brief labelled contemporaneous.
6. **Phase 1 rollback.** Drop the new tables, views and functions. The legacy table is untouched.
   - Leftovers that are harmless: the two new nullable columns on `detected_scenarios` and the repaired trigger function.
   - Leftovers on `daily_briefings`: the new columns, constraints, index and trigger. Drop them explicitly.
7. **Supabase notes.**
   - Each file wraps itself in `BEGIN`/`COMMIT`. In the SQL editor it runs atomically; via the CLI the explicit transaction is harmless.
   - The validation used Postgres 16 locally; production runs 17.6. Nothing here is specific to version 17; `UNIQUE NULLS NOT DISTINCT` needs version 15 or later.
   - The `storage.buckets` insert was tested against a stub table, so it is untested on the real Storage schema.

## 8. Size estimates vs. the 500 MB cap

These figures were measured, not guessed: 30 synthetic days at the design load were loaded into the scratch database and measured (`tests/sizing_output.txt`). The load per day was:
- 400 articles;
- about 150 stories;
- 1.2 topics per story;
- 40 topics in `topic_daily`;
- 10 alerts;
- 1 run (the real 14-input Day 221 table) and 5 scenario rows;
- 5 briefs × 4 documents.

| Table | KB/day (with churn) | KB/day (compact) |
|---|---|---|
| stories | 137.9 | 72.8 |
| story_articles | 104.5 | 94.9 |
| story_topics | 43.2 | 39.5 |
| report_documents (rows only) | 17.3 | 14.7 |
| intel_alerts | 14.7 | 13.6 |
| scenario_daily | 12.3 | 11.2 |
| topic_daily | 10.4 | 8.5 |
| scenario_runs | 7.2 | 5.1 |
| **All new tables** | **≈ 0.34 MB/day** | **≈ 0.25 MB/day** |
| articles at 400/day (existing table, same load) | 0.29 MB/day | 0.28 MB/day |

**Projection:**
- Growth: new tables 0.25–0.34 MB/day, articles 0.29, other existing writers about 0.06 (DB audit). Total ≈ **0.6–0.7 MB/day**, or about 220–255 MB a year.
- One-off backfills:
  - News index plus stories for the missing Days 36–218, at up to 400 articles a day: up to about 116 MB. The W1 scout sets the real volume and should cap it.
  - Scenario history for 185 days: about 3 MB.
  - Briefings (159 General plus about 78 weekly, with Arabic doubling the text): about 5 MB.
- From 38.75 MB today:
  - **With the full news and story backfill, the cap is reached in about 490 days (around February 2028).**
  - Without the story backfill: about 650–770 days.
- Mitigation: the size-triggered summary stripper proposed in DB audit §F13, which acts at 350 MB, applied to `articles.summary`. The new tables have no large text columns.

**Supabase Storage (1 GB, separate from the database):** document sizes were *not* measured.
- Assumptions: docx 40–80 KB, PDF 100–300 KB.
- docx only, 5 briefs a day × 2 languages: 0.4–0.8 MB a day, so about 3.4–6.8 years until 1 GB.
- **Storing PDF as well: 1.4–3.8 MB a day, so 1 GB in 9–24 months. PDF is the cap risk.**
- The backfill (about 440 briefs × 2 languages) is 35–70 MB as docx, plus 88–264 MB if PDFs are stored.
- Signed-URL downloads count against the free-plan egress quota. Check the current figure before launch.

## 9. Acceptance tests builders must pass

**In the database** (`tests/10_acceptance_tests.sql`): 104/104 must pass on a fresh scratch database built from the fixture and every migration.
- **S01–S36 (scenario registry):** exact compatibility in both directions; legacy row counts and provenance; Day 221 values and its 14 stored inputs; rejection of missing, invalid or unused inputs, of runs without inputs, of legacy rows outside the import, of direct legacy writes, of edits and deletes, of non-100 sums, of incomplete sets, of overrides without a reason, of future days, of publishing a KEEP_FROZEN run, of backdated provenance, of direct status changes and inserts, of early fades, of active→retired, and of births backed by a single source; immutable events; the approval-trigger fix; closed NULL-CHECK leaks.
- **L01–L15 (lifecycle, end to end):** birth on Day 190 → rise → 13 days with no transition → day 14 fading with 14 readings as evidence → recovery at exactly 10% → a missing day breaks the streak → fades again → the job cannot retire → the operator retires (`retired_day` 222, history kept) → retired is terminal → a defining market resolves and the scenario fades immediately → the compatibility view is unchanged.
- **R01–R25 (reports):** provenance backfill; old writers still work; a past day cannot claim contemporaneous; no relabelling; foreign key and unique index; weekly periods (including half-open ones); the document path, checksum, validation, RTL and Arabic-edition checks; foreign-key RESTRICT; the renderer queue; the report-type lifecycle (the job cannot activate or retire); no deletes.
- **T01–T17 (stories):** verbatim titles; the derived mix and language counts; an empty count check; stated geolocation only (including partial cases); retention (articles, stories and members); snapshot integrity; no party label without an outlet; merges; candidate alerts need 2 independent hosts; immutable alert evidence; the reviewer requirement; deduplication.
- **P01–P10 (privileges):**
  - no anon or authenticated write privilege on any new or touched table, and no policy granted to `public`;
  - write policies are `service_role`-only;
  - anon cannot insert, cannot read alerts and cannot execute lifecycle functions;
  - anon sees only approved links and only non-candidate report types;
  - signed-in users can read briefings;
  - `service_role` cannot delete but can run the job path.

**Outside the database** (each builder adds these to their pull request):
1. **W2 recompute.** For every `scenario_runs` row, `compute(method_version, inputs)` must reproduce the published `scenario_daily` values exactly, Day 221 included: A 23, B 44, C 5, D 28, E NULL.
2. **W2 API parity.** The PostgREST JSON for `scenario_probabilities?order=conflict_day.asc` before the migration must equal the JSON after it, byte for byte. The pages `/`, `/scenarios`, `/warroom`, `/timeline` and `api-scenarios` must render the same.
3. **W2 job.** A dry run of `scenario_daily.yml` on today's markets must write one run plus rows, publish them, run the tick, and fail loudly on any CHECK violation.
4. **W3.** The admin user reaches any brief from the 221 days in at most 3 clicks, using `v_briefing_catalog`. Every document listed in `report_documents` downloads through a signed URL. Its sha256 matches. It passes `office/validate.py`. Arabic documents are RTL.
5. **W4.** A planted test article pair — two independent outlets, one stated place — must appear, cluster, produce a story with the quoted geolocation, and raise the expected alert within one hourly cycle. It must cost nothing on any AI API.
6. **All builders.** `npm run type-check`, `lint` and `build:cf` must be green. A verifier re-runs `tests/run_validation.sh`.

## 10. Production findings made while designing (for the lead)

1. **The approval trigger is broken in production.** `activate_new_scenario_alert()` reads `NEW.label`, `NEW.new_actor` and `NEW.new_instrument`, but production `detected_scenarios` has `scenario_label` and none of those columns. Approving any candidate, including today's F "Pact Expansion", raises an error. **Fixed in 100000 §11** (test S33).
2. **Signed-in users likely get zero briefings.** This is plausible but was not tested end to end against production. The only read policy on `daily_briefings` is `TO anon`, while `hooks/useBriefing.ts` uses `createBrowserClient` from `@supabase/ssr`, which sends the user's JWT and so runs as the `authenticated` role.
